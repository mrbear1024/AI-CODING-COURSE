# 第15章：Git 进阶技巧

## 概念讲解

恭喜你已经掌握了 Git 的基础操作！但在真实的开发工作中，你会遇到更复杂的场景：提交历史变得混乱、多个分支同时修改了同一行代码、写到一半需要临时切换任务……本章将教你一系列进阶技巧，让你从 Git 新手进化为 Git 高手。

## 类比说明

如果说基础 Git 操作是学会了开车的油门和刹车，那么本章的内容就是学会倒车入库、高速变道和紧急避障——都是实际上路后必不可少的技能。

## 实操步骤

### 1. Rebase（变基）— 让历史更整洁

**类比**：想象你在写一篇文章，写了好几个版本的草稿。在提交给编辑之前，你想把那些凌乱的修改整理成一个干净的版本。Rebase 就是这个"整理"的过程。

**Rebase 与 Merge 的区别**：

- **Merge（合并）** 会保留所有分支的历史，像两条河流汇合，留下一个合并节点。
- **Rebase（变基）** 会把你的提交"搬"到目标分支的最前面，让历史看起来像一条直线。

```bash
# 在你的功能分支上执行
git checkout my-feature
git rebase main
```

**什么时候用哪个？**

- 个人分支、还没推送到远程的提交 → 用 **Rebase**，保持历史整洁。
- 已经推送到远程、多人协作的分支 → 用 **Merge**，避免改写别人的历史。

**黄金法则**：永远不要对已经推送到公共仓库的提交执行 Rebase。这就像篡改已经发表的报纸——会让所有读者困惑。

### 2. Worktree（工作树）— 同时打开多个平行世界

**类比**：你正在厨房做一道复杂的菜（在 feature 分支上开发），突然有人说主菜有个紧急 Bug 要修。以前你只有一个厨房，必须先把东西收拾好才能腾出空间。**Worktree** 让你同时拥有多个厨房，每个厨房独立工作，互不干扰。

```bash
# 为 main 分支创建一个新的工作目录
git worktree add ../project-hotfix main

# 现在你可以在新目录里修 Bug
cd ../project-hotfix
# ...修复代码、提交...

# 修完后删除工作树
git worktree remove ../project-hotfix
```

**实用场景**：

- 在开发新功能的同时修复紧急 Bug，无需 stash 或切换分支。
- 同时查看和对比两个分支的代码。
- 在一个工作树里运行测试，另一个工作树里继续写代码。

比起 `git stash` 后切换分支，Worktree 的优势是你的两个工作环境完全独立，互不打扰。

### 3. Cherry-pick — 精确"摘取"某次提交

**类比**：你种了一棵苹果树（一个分支），上面结了很多果子（多次提交）。Cherry-pick 就是从这棵树上只摘一颗你想要的苹果，放到另一棵树上。

```bash
# 先用 git log 找到你想要的提交的哈希值
git log --oneline

# 切换到目标分支
git checkout main

# 摘取特定的提交
git cherry-pick abc1234
```

**使用场景**：某个 Bug 修复提交在开发分支上，你想把这个修复也应用到发布分支上，但不想合并整个开发分支。

### 4. Stash（暂存）— 临时保存未完成的工作

**类比**：你正在画一幅油画，突然有人让你帮忙画另一幅。你不想把颜料洗掉，于是把调色板暂时放进抽屉里。等帮完忙，再从抽屉里取出来继续画。

```bash
# 暂存当前的修改
git stash

# 去做其他事情...
git checkout other-branch
# ...完成后切回来

# 取出暂存的修改
git checkout my-branch
git stash pop
```

常用命令：

```bash
git stash list          # 查看所有暂存的内容
git stash pop           # 取出最近一次暂存并删除记录
git stash apply         # 取出最近一次暂存但保留记录
git stash drop          # 丢弃某个暂存
```

### 5. 解决 Merge Conflicts（合并冲突）

**类比**：你和同事同时编辑同一份文件的同一段话。你改成了版本 A，他改成了版本 B。Git 不知道该听谁的，于是标记出冲突，让你自己决定。

当冲突发生时，Git 会在文件中插入这样的标记：

```
<<<<<<< HEAD
这是你的修改内容
=======
这是对方的修改内容
>>>>>>> feature-branch
```

**解决步骤**：

1. 打开有冲突的文件。
2. 找到 `<<<<<<<`、`=======`、`>>>>>>>` 标记。
3. 决定保留哪个版本（或两者结合），删除标记符号。
4. 保存文件，然后：

```bash
git add 冲突文件名
git commit -m "解决合并冲突"
```

**小贴士**：冲突并不可怕，它只是 Git 在礼貌地问你："这里我拿不准，你来决定。"

### 6. Interactive Rebase（交互式变基）— 整理提交历史

**类比**：你写了五条朋友圈动态，发出去之前想整理一下——把第二条和第三条合并、把第四条的文字改一改、把第一条删掉。Interactive Rebase 就是这种"发布前的编辑"。

```bash
# 整理最近 3 次提交
git rebase -i HEAD~3
```

这会打开一个编辑器，显示：

```
pick abc1234 添加登录功能
pick def5678 修复登录按钮样式
pick ghi9012 补充登录功能的注释
```

你可以把 `pick` 改成：

- **squash**（合并）：把这个提交合并到前一个提交里。
- **reword**（改写）：修改提交信息。
- **drop**（丢弃）：删除这个提交。

### 7. git reflog — 最后的安全网

**类比**：即使你在时光机里做了一些糟糕的操作（比如误删了分支或错误的 Rebase），`reflog` 就像黑匣子一样，记录了你在 Git 中的每一步操作。

```bash
git reflog
```

你会看到所有操作记录。找到你想恢复的那个状态的哈希值，然后：

```bash
git reset --hard abc1234
```

**记住**：只要你提交过的东西，几乎都能通过 `reflog` 找回来。它是你的终极保险。

## AI 辅助练习

1. **Rebase 练习**：
   - 提示词：`"我有一个功能分支落后了主分支 5 个提交，请一步步教我用 rebase 同步最新代码。"`

2. **Worktree 练习**：
   - 创建一个仓库，在 feature 分支上开发到一半。
   - 用 `git worktree add` 创建新工作树来修复 main 分支的一个 Bug。
   - 完成后清理工作树。

3. **冲突解决练习**：
   - 提示词：`"请模拟一个 Git 合并冲突的场景，然后教我一步步解决它。"`

4. **Cherry-pick 练习**：
   - 创建两个分支，在其中一个分支上做多次提交。
   - 用 `cherry-pick` 只挑选其中一个提交应用到另一个分支。

5. **Reflog 救援练习**：
   - 故意删除一个分支，然后用 `git reflog` 和 `git checkout -b` 把它恢复回来。

## 本章小结

| 技巧 | 类比 | 核心命令 | 使用场景 |
|------|------|---------|---------|
| Rebase（变基） | 整理草稿再提交 | `git rebase main` | 保持提交历史整洁 |
| Worktree（工作树） | 同时拥有多个厨房 | `git worktree add` | 同时处理多个分支的任务 |
| Cherry-pick | 从树上摘一颗苹果 | `git cherry-pick 哈希值` | 只要某个特定提交 |
| Stash（暂存） | 把调色板放进抽屉 | `git stash` / `git stash pop` | 临时保存未完成的工作 |
| 合并冲突 | 两人改同一段话 | 手动编辑 + `git add` | 合并时遇到冲突 |
| Interactive Rebase | 发朋友圈前编辑 | `git rebase -i HEAD~N` | 合并/修改/删除提交 |
| Reflog | 黑匣子记录 | `git reflog` | 误操作后的救命稻草 |

进阶技巧不需要一次全记住。建议先把 Stash 和解决冲突练熟——这两个你很快就会用到。其他技巧在你遇到具体场景时再查阅本章即可。Git 的强大之处在于，它几乎总有办法让你从任何困境中脱身！
