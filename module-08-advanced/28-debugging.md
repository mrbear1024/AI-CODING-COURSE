# 第28章：调试与排错技巧

## 引言：Bug 是程序员最好的老师

如果你写代码时从来没遇到过错误，那只能说明一件事——你还没开始写代码。

Bug（程序缺陷）就像做菜时的失误：有时候盐放多了（参数错误），有时候忘了开火（遗漏关键步骤），有时候用错了食材（类型错误）。每一次犯错、排查、修复的过程，都会让你成为更好的"厨师"。

本章将教你如何**系统地**找出问题并修复它，而不是对着屏幕干瞪眼。

---

## 一、读懂错误信息——它们其实在帮你

很多初学者看到红色的错误信息就慌了。但其实，**错误信息是程序在跟你说话**，它在告诉你："嘿，第 42 行有个问题，你拼错了一个单词。"

把错误信息想象成医生的诊断报告：你不需要懂每一个医学术语，但你至少要看懂"哪里痛"和"可能的原因"。

### 错误信息的三个关键部分

1. **错误类型**（Error Type）：什么性质的问题
2. **错误描述**（Error Message）：具体出了什么错
3. **位置信息**（Stack Trace）：问题发生在哪一行、哪个文件

```
TypeError: Cannot read properties of undefined (reading 'name')
    at getUserInfo (app.js:42:15)
    at main (app.js:10:3)
```

翻译一下：在 `app.js` 文件的第 42 行，你试图读取一个 `undefined`（未定义）值的 `name` 属性。就像你试图打开一扇不存在的门上的锁——门都没有，何来锁呢？

## 二、三种常见错误类型

### 1. 语法错误（Syntax Error）

**类比：** 写中文时漏了标点或用了错别字，别人读不懂。

```javascript
// 少了一个括号
function sayHello( {
  console.log("Hello")
}
```

**特点：** 程序根本无法运行，浏览器/编译器会直接报错。这是最"友好"的错误，因为它会告诉你确切的位置。

### 2. 运行时错误（Runtime Error）

**类比：** 菜谱写得没问题，但你打开冰箱发现鸡蛋用完了——执行过程中才暴露的问题。

```javascript
let user = null;
console.log(user.name); // TypeError! user 是 null，没有 name 属性
```

**特点：** 代码语法没问题，但运行到某一步时"翻车"了。通常跟数据有关。

### 3. 逻辑错误（Logic Error）

**类比：** 菜做出来了，但你把糖当成盐放了——程序能跑，但结果不对。

```javascript
// 本意是计算折扣价，但写反了
function getDiscountPrice(price, discount) {
  return price + price * discount; // 应该是减号！
}
```

**特点：** 没有任何报错，程序"正常"运行，但输出结果不符合预期。这是最难发现的一种错误。

## 三、调试工具：你的"显微镜"

### 浏览器 DevTools（开发者工具）

按 `F12` 或右键选"检查"（Inspect）即可打开，这是前端开发者最重要的工具。

- **Console（控制台）面板：** 查看错误信息和 `console.log()` 的输出
- **Elements（元素）面板：** 查看和修改 HTML/CSS，实时看效果
- **Network（网络）面板：** 查看所有网络请求，检查 API 调用是否成功
- **Sources（源代码）面板：** 设置断点（Breakpoint），逐行执行代码

**断点调试就像慢动作回放：** 你可以让程序在某一行暂停，然后一步一步往下走，观察每个变量的值。这比到处加 `console.log` 高效得多。

### 服务器日志（Server Logs）

后端程序的错误不会显示在浏览器里，而是记录在服务器日志中。

```bash
# 查看 Node.js 应用的输出
npm run dev

# 常见的日志关键词
[ERROR]   # 错误——必须处理
[WARN]    # 警告——可能有隐患
[INFO]    # 信息——正常运行记录
```

**类比：** 浏览器 DevTools 是你站在餐厅前台观察顾客反馈，服务器日志是你走进后厨查看烹饪过程。

## 四、系统化调试流程

遇到 Bug 时，不要随机修改代码碰运气。请按这个四步法：

### 步骤 1：复现（Reproduce）
> "它在什么情况下出错？"

确保你能稳定地重现这个问题。如果问题时有时无，记录下出现问题时的具体操作步骤。

### 步骤 2：定位（Isolate）
> "问题到底出在哪一行？"

使用 `console.log`、断点调试或注释掉部分代码，逐步缩小问题范围。像二分查找一样——先确认前半部分还是后半部分有问题。

### 步骤 3：修复（Fix）
> "怎么改才对？"

找到根因后，做最小的改动来修复问题。不要顺手改一堆不相关的东西。

### 步骤 4：验证（Verify）
> "真的修好了吗？会不会引入新问题？"

修复后，重新测试原来的场景，同时测试相关功能确保没有"按下葫芦浮起瓢"。

## 五、用 AI 辅助调试

AI 是你最好的调试伙伴。把错误信息完整地丢给 AI，成功率极高。

### 提问模板

```
我在运行以下代码时遇到错误：

[粘贴你的代码]

错误信息是：
[粘贴完整的错误信息]

我期望的结果是：[描述你想要什么效果]
实际的结果是：[描述实际发生了什么]

请帮我分析原因并给出修复方案。
```

**关键点：** 提供完整的上下文。只说"我的代码不工作了"就像跟医生说"我不舒服"——信息太少，无法诊断。

## 六、常见初学者错误速查表

| 错误现象 | 可能原因 | 解决方案 |
|---------|---------|---------|
| 页面一片空白 | JavaScript 报错导致渲染中断 | 打开 Console 查看错误 |
| API 返回 404 | 请求地址拼写错误 | 检查 URL 和路由配置 |
| API 返回 500 | 服务器端代码报错 | 查看服务器日志 |
| 样式不生效 | CSS 选择器写错或被覆盖 | 用 Elements 面板检查 |
| 变量值是 undefined | 变量未赋值或拼写错误 | 检查变量名和赋值逻辑 |
| 跨域错误（CORS） | 前端和后端域名不一致 | 后端配置 CORS 允许规则 |

## AI 辅助练习

1. **刻意制造错误：** 在你之前写的项目里故意引入一个 Bug，然后用本章方法找到并修复它
2. **错误信息翻译：** 收集 5 条你曾遇到的错误信息，用自己的话翻译成中文，理解它们在说什么
3. **用 AI 调试：** 下次遇到报错时，按上面的模板向 AI 提问，对比 AI 的回答和你自己的分析

---

## 本章小结

- 错误信息不是敌人，而是**帮你定位问题的指南针**
- 三种错误类型：语法错误（最好找）、运行时错误（跟数据相关）、逻辑错误（最难找）
- 浏览器 DevTools 是前端调试的核心工具，`F12` 打开即用
- 遵循"复现 -> 定位 -> 修复 -> 验证"的系统化流程
- 善用 AI 辅助调试，但要提供**完整的上下文信息**
- 每一个 Bug 都是一次学习机会——修过的 Bug 越多，你就越强
