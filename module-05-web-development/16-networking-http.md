# 第16章：网络基础与 HTTP

## 引言：互联网是怎么工作的？

你有没有想过，当你在浏览器里输入一个网址，按下回车键，网页是怎么"变"出来的？这背后其实是一套精密但并不神秘的系统在运作。

**把互联网想象成一个巨大的邮政系统。** 你写了一封信（请求），上面写着收件人地址（网址），邮局（网络基础设施）会帮你把信送到目的地（服务器），对方读完信后，再把回信（响应）寄回给你。整个过程就是这么简单——只不过速度快了几百万倍。

---

## 核心概念讲解

### URL（统一资源定位符）—— 互联网上的"门牌号"

每个网页都有一个独一无二的地址，叫做 **URL（Uniform Resource Locator）**。比如：

```
https://www.example.com/products?category=books&page=2
```

这个地址可以拆解成几个部分：

| 部分 | 示例 | 类比 |
|------|------|------|
| **协议（Protocol）** | `https://` | 寄信的方式（挂号信 vs 普通信） |
| **域名（Domain Name）** | `www.example.com` | 收件人的名字 |
| **路径（Path）** | `/products` | 收件人家里的具体房间 |
| **查询参数（Query Parameters）** | `?category=books&page=2` | 信里附带的具体要求 |

### 域名（Domain Name）与 IP 地址（IP Address）

域名就像人名，好记又好认。但计算机之间真正通信用的是 **IP 地址（Internet Protocol Address）**——一串数字，比如 `93.184.216.34`。

这就好比你告诉出租车司机"去天安门"，司机的导航系统会把它转换成具体的经纬度坐标。帮你完成这个"翻译"工作的系统，就是 **DNS（Domain Name System，域名系统）**。

**DNS 的工作流程就像查电话簿：**
1. 你输入 `www.example.com`
2. 浏览器问 DNS 服务器："这个名字对应的 IP 地址是什么？"
3. DNS 回答："是 `93.184.216.34`"
4. 浏览器拿着这个 IP 地址去找真正的服务器

### HTTP/HTTPS —— 客户端和服务器的"对话规则"

**HTTP（HyperText Transfer Protocol，超文本传输协议）** 是浏览器和服务器之间的"语言"。**HTTPS** 是它的加密版本，就像把普通信换成了密封的保密信件。

把这个过程想象成**在餐厅点餐**：

1. **你（客户端/Client）** 坐下来看菜单
2. **你向服务员说出你的需求（发送请求/Request）**
3. **厨房（服务器/Server）** 收到订单，开始准备
4. **服务员把菜端上来（返回响应/Response）**

### 请求方法（Request Methods）—— 你想做什么？

HTTP 定义了几种"动作"，告诉服务器你想干什么：

| 方法 | 含义 | 餐厅类比 |
|------|------|----------|
| **GET** | 获取数据 | "请给我看看菜单" |
| **POST** | 创建新数据 | "我要下一个新订单" |
| **PUT** | 更新已有数据 | "我要把那道菜换成另一道" |
| **DELETE** | 删除数据 | "请取消我刚才点的那道菜" |

### 状态码（Status Codes）—— 服务器的"回话"

服务器收到你的请求后，会用一个数字告诉你结果如何：

- **200 OK** —— "一切顺利，这是你要的东西！"（就像服务员微笑着把菜端上来）
- **301 Moved Permanently** —— "这家店搬了，新地址在这里"（永久重定向）
- **404 Not Found** —— "对不起，我们没有这道菜"（你请求的页面不存在）
- **403 Forbidden** —— "这是 VIP 专区，你进不去"（没有权限）
- **500 Internal Server Error** —— "厨房着火了！"（服务器内部出错）

记住这个规律：**2xx 表示成功，3xx 表示跳转，4xx 表示你的问题，5xx 表示服务器的问题。**

### RESTful API —— 一套优雅的设计约定

**API（Application Programming Interface，应用程序编程接口）** 是程序之间对话的窗口。**RESTful API** 是一种流行的 API 设计风格，它用直观的 URL 和 HTTP 方法来组织接口。

举个例子，一个管理图书的 RESTful API 可能长这样：

| 操作 | 方法 | URL |
|------|------|-----|
| 获取所有图书 | GET | `/api/books` |
| 获取某本图书 | GET | `/api/books/42` |
| 添加新图书 | POST | `/api/books` |
| 更新图书信息 | PUT | `/api/books/42` |
| 删除某本图书 | DELETE | `/api/books/42` |

看到规律了吗？URL 表示"资源是什么"，HTTP 方法表示"要对资源做什么"。这就是 REST 的核心思想——**简洁、直观、统一**。

### Headers 和 Body —— 信封上的信息和信的内容

每个 HTTP 请求和响应都包含两部分：

- **Headers（请求头/响应头）**：附加信息，就像信封上写的发件人、日期、信件类型等。常见的有：
  - `Content-Type: application/json`（告诉对方"信的内容是 JSON 格式的"）
  - `Authorization: Bearer xxx`（"这是我的身份证明"）

- **Body（请求体/响应体）**：正文内容，就是信里面真正要说的话。比如发送一个 POST 请求来创建新用户：

```json
{
  "name": "小明",
  "email": "xiaoming@example.com"
}
```

## 实操步骤：用浏览器观察 HTTP 请求

不需要写任何代码，你现在就可以"看到" HTTP 请求！

1. 打开 Chrome 浏览器，按 **F12** 打开开发者工具
2. 点击 **Network（网络）** 标签
3. 在地址栏输入任意网址，比如 `https://www.baidu.com`
4. 观察 Network 面板中出现的请求列表
5. 点击任意一条请求，查看它的 **Headers**、**Response** 等信息

你会看到浏览器为了加载一个网页，发送了几十甚至上百个请求——获取 HTML、CSS、JavaScript、图片等等。

## 本章小结

| 概念 | 一句话总结 |
|------|-----------|
| URL | 互联网上资源的唯一"门牌号" |
| DNS | 把域名翻译成 IP 地址的"电话簿" |
| HTTP/HTTPS | 浏览器和服务器之间的对话规则 |
| 请求方法 | GET 获取、POST 创建、PUT 更新、DELETE 删除 |
| 状态码 | 服务器用数字告诉你请求的结果 |
| RESTful API | 一种简洁直观的 API 设计风格 |
| Headers/Body | 请求的"信封信息"和"信的内容" |

记住那个餐厅的比喻：你是顾客（客户端），服务员帮你传话（HTTP），厨房负责做菜（服务器）。理解了这个流程，你就理解了整个互联网通信的基础！
